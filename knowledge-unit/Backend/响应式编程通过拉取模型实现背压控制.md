## 1. 它解决了什么问题？
在数据流处理中，生产者（上游数据源）往往比消费者（下游处理逻辑）快得多。如果生产者无限制地向消费者推送数据，消费者处理不过来时数据会在内存缓冲区无限堆积，最终 OOM。传统的命令式并发模型（包括虚拟线程）没有内置机制来协调生产者和消费者之间的速率。
## 2. 它的核心矛盾是什么？
**推送模型（push）简单但危险，拉取模型（pull）安全但复杂。**
推送模型：数据来了就发，代码好写，但消费者需要自己保护自己（限流、缓冲、丢弃策略）。
拉取模型：消费者控制节奏，天然安全，但需要在协议层面约定 request/response 交互。
## 3. 它的本质模型是什么？
**Reactive Streams 协议的拉取模型（pull model）。**
消费者通过 `request(N)` 声明自己可以处理 N 条数据，生产者只推送 N 条后暂停，等待消费者发出下一个 `request`。控制流从消费者流向生产者，速率由最慢的环节决定。
交互时序：
1. Subscriber 调用 Publisher.subscribe() 订阅
2. Publisher 回调 Subscriber.onSubscribe(Subscription s)
3. Subscriber 调用 s.request(N) 声明"我能处理 N 条"
4. Publisher 最多推送 N 条数据（onNext），然后暂停
5. Subscriber 处理完后再次调用 request(M)
## 4. 它还能解释什么？
- **TCP 滑动窗口**：接收方通过 window size 告诉发送方"我 buffer 还剩多少"，发送方不会发送超过窗口大小的数据。这是网络层的背压控制。
- **Kafka Consumer**：消费者 poll() 主动拉消息，速率由消费者控制。
- **Go Channel**：`ch := make(chan int, 10)` 缓冲大小 10，满了 sender 阻塞 → 这是背压的简化实现。
## 5. 认知变化
**以前我以为**：响应式就是"异步 + 非阻塞"的另一种写法，虚拟线程出来后响应式就过时了。
**现在我认为**：响应式和虚拟线程解决的是不同问题。虚拟线程解决"大量并发任务"（每个线程一个请求），响应式解决"数据流速率不匹配"。web CRUD 场景用虚拟线程更好，数据流管道场景用响应式更好。两者互补而非替代。
## 6. 最终压缩
> 响应式通过 Reactive Streams 协议的拉取模型实现背压：消费者用 request(N) 告诉生产者自己的处理能力，生产者只推 N 条后暂停。控制流从消费者流向生产者，速率以最慢环节为准。适合数据流管道但不适合 web CRUD。
