## 同步器的解剖：六个构建块构成所有同步工具

**解决的问题：**

Java 提供了锁、信号量、阻塞队列、读写锁等多种同步器——它们看似功能各异，但内部设计有没有统一框架？理解这个框架能否帮助设计新的同步器？

**本质模型：**

所有同步器（锁、信号量、阻塞队列、读写锁）共享六个构建块，区别仅在于内部状态和对这些块的具体实现：

1. State（状态）：决定线程能否被准入的内部数据。Lock 是 boolean，BoundedSemaphore 是 int + bound，BlockingQueue 是 List + limit。
2. Access Condition（准入条件）：基于状态判断线程能否继续。总是放在 while 循环中检查以防护 Spurious Wakeup。
3. State Changes（状态变更）：线程获得准入后立即修改状态，阻止其他线程。准入和释放时各一次。
4. Notification Strategy（通知策略）：三种——notifyAll()（所有等待线程）、notify()（随机一个）、或 notify 特定线程（每线程独立监视器对象，用于公平锁）。
5. Test-and-Set Method（测试并设方法）：先测试准入条件再设置状态，两步必须原子。lock()/take()/enqueue() 属于此类。
6. Set Method（直接设方法）：只设置状态不测试条件。unlock() 属于此类——持锁线程无需测试就能释放。

这个框架是 Doug Lea 设计 J.U.C 时的独立发现，证明了好的设计模式具有收敛性。

**权衡：**

这个框架是描述性的不是规范性的——不是每个同步器都包含全部六块，不包含的也不是「错的」。但当你需要自己设计同步工具时，遍历这六个问题可以确保没有遗漏关键设计决策（尤其是最容易忽视的 Notification Strategy）。

**迁移：**

六块框架不仅适用于 Java 同步器——任何并发/分布式协调机制都能对应：分布式锁的 State 是 Redis/ZK 中的 key-value，Access Condition 是「key 不存在」，Test-and-Set 是 SETNX，Notification Strategy 是 Pub/Sub 或轮询。甚至 Kubernetes 的 controller reconcile 也符合这个模型。
