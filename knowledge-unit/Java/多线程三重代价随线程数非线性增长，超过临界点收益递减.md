## 1. 它解决了什么问题？
多线程引入了哪些隐性成本？什么时候成本超过收益？
## 2. 它的核心矛盾是什么？
收益随线程数增长但边际递减，代价随线程数增长且非线性递增——两者在某一点交叉后就是负收益。
## 3. 它的本质模型是什么？
多线程有三重代价，且随线程数非线性增长：
- 设计复杂度：多线程 bug 是非确定性的（Heisenbug），难以复现和修复
- 上下文切换开销：保存/恢复寄存器、栈指针、刷新缓存，线程数远超核心数时切换吃掉 CPU 时间
- 资源消耗：每个线程需要栈内存（Java 默认约1MB）和 OS 资源，线程泄露比内存泄露更难发现
经验法则（Brian Goetz 公式）：线程数 = CPU核数 × (1 + IO等待时间/CPU计算时间)
- CPU密集：线程数 = 核数
- IO密集：线程数 ≈ 2倍核数
## 4. 它还能解释什么？
- 协程/Goroutine 虽更轻量，但无限制创建同样会耗尽资源
- 线程泄露表现为系统逐渐变慢，最终 OOM，但不容易第一时间联想到线程问题
- Virtual Threads 解决的是资源消耗这一层（动态栈），但不解决设计复杂度和切换开销
## 5. 认知变化
**以前我以为：** 多线程代价主要是切换开销
**现在我认为：** 三重代价叠加且非线性增长，其中线程泄露比内存泄露更隐蔽；收益和代价在某点交叉后就是负收益
## 6. 最终压缩
> 多线程代价有三层：设计复杂度、上下文切换、资源消耗，随线程数非线性增长。收益与代价存在交叉点，超过就是负收益。
