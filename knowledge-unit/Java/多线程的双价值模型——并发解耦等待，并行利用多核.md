## 1. 它解决了什么问题？
多线程教程列举了四个好处：更好的 CPU 利用率、更简单的设计（某些场景）、更好的响应性、更公平的资源分配。这四个好处看似是不同场景下的独立收益，但它们底层有没有统一的解释？
## 2. 它的核心矛盾是什么？
I/O 速度远慢于 CPU 速度（磁盘、网络、用户输入），导致 CPU 在等待时空转浪费；同时，单核性能增长见顶，多核成为趋势。
## 3. 它的本质模型是什么？
多线程有两个独立价值，由不同的物理约束驱动：
- **并发 — 解耦等待与计算**：I/O 速度 << CPU 速度 → CPU 不闲等，切换去做别的
- **并行 — 利用多核同时计算**：单核性能见顶，核数增加 → 把计算拆到多个核同时跑
四个好处可以这样归因：
- CPU 利用率 → 并发模型：解耦 I/O 等待与计算
- 简单设计 → 并发模型：用独立线程代替手动编排
- 响应性 → 并发模型：UI 线程等用户，worker 线程做任务
- 公平性 → 并发模型：不让一个慢请求阻塞全部
而纯 CPU 密集型的多核加速则属于并行模型。
## 4. 它还能解释什么？
- **Node.js 事件循环**：只用并发模型（单线程非阻塞 I/O），不用并行
- **Go goroutines**：轻量级并发 + 多核并行，两者都用
- **MapReduce**：并行模型扩展到分布式规模
- **微服务架构**：不同服务处理不同请求（并发），同一服务多实例（并行）
## 5. 认知变化
**以前我以为：** 多线程的几个好处是不同场景的独立收益。
**现在我认为：** 表面的四个好处实际上由两个更底层的独立模型驱动——并发（解耦等待与计算）和并行（利用多核），理解这个二分法比记住四个好处更有价值。
## 6. 最终压缩
> 多线程 = 并发（解耦 I/O 等待）+ 并行（利用多核），两个独立价值由不同物理约束驱动。
