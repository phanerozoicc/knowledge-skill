## 1. 它解决了什么问题？
多线程的收益（CPU利用率、响应性、公平性）是可测量、可预期的，但主要代价——并发 bug——具有不可复现、不可预测、难以定位的特性。这两者在性质上是不对称的。因此工程策略不应该教开发者"更好地掌握并发复杂度"，而应该"隔离复杂度"和"消灭共享状态"。
## 2. 它的核心矛盾是什么？
收益是确定性的，代价是不确定性的。追求最大性能需要手动精细同步，但这直接暴露在并发 bug 的不可预测风险之下。
## 3. 它的本质模型是什么？
并发风险的不对称性要求双路策略：
- **抽象隔离**：不直接碰 synchronized/wait/notify，用线程池、BlockingQueue、ConcurrentHashMap
- **消灭共享状态**：没有共享就没有竞争，用不可变对象、ThreadLocal、消息队列
资源消耗和上下文切换是"可感知的代价"（应用慢了能看到），但并发 bug 是"不可感知的代价"（可能只在生产环境特定时序下偶发）。后者才是真正的工程风险。
## 4. 它还能解释什么？
- **java.util.concurrent 的存在理由**：把并发复杂度封装为工具，让开发者不需要每次自己处理
- **分布式系统的幂等设计**：用"消灭不确定性"的思路处理分布式并发
- **数据库事务隔离级别**：用"抽象并发复杂度"的思路让应用层不用关心锁
## 5. 认知变化
**以前我以为：** 多线程的三个代价（设计复杂度、上下文切换、资源消耗）是同等严重的。
**现在我认为：** 设计复杂度远比其他两个危险，因为资源消耗是自调节的（你会注意到应用慢了），而并发 bug 是不可预测、不可复现的。
## 6. 最终压缩
> 多线程收益可预期、代价不可预期，因此工程策略应双路并行：抽象隔离并发复杂度 + 从源头消灭共享状态。
