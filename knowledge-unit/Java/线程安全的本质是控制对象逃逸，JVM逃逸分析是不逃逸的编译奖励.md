## 1. 它解决了什么问题？
多线程下什么代码安全什么不安全？对象逃逸是什么，怎么发现和修复？JVM逃逸分析又是什么？
## 2. 它的核心矛盾是什么？
对象天然活在堆上被所有线程共享，但线程安全要求对象只被一个线程碰。逃逸是两者之间的缝隙。
## 3. 它的本质模型是什么？
**Thread Control Escape Rule：** 资源的创建、使用、销毁都在同一个线程控制下且从未逃逸，则线程安全。
**五种常见逃逸场景：**
1. 赋值给成员变量或静态变量
2. 通过方法返回值逃逸
3. 传给外部方法/回调（最隐蔽）
4. 内部类/Lambda捕获外部引用（最高频）
5. 发布到全局集合
**线程安全不是类的属性，是使用方式的属性：** 同一个非线程安全类，每个线程各用各的实例就安全。
**五种修复策略：**
1. 不逃逸（最根本）
2. 不可变对象（逃逸了但改不了）
3. 防御性拷贝（返回副本）
4. 加锁保护（逃逸不可避免就锁）
5. 线程封闭/ThreadLocal（人为制造不逃逸）
**JVM逃逸分析（编译优化）：** JIT编译时检测对象是否逃逸出方法/线程，如果没逃逸则自动优化：
- 栈上分配：无GC压力
- 标量替换：对象拆成基本类型直接用寄存器
- 锁消除：对象没逃逸则synchronized没必要
编码时避免逃逸和JVM逃逸分析优化是同一件事的两个视角。
## 4. 它还能解释什么？
- Netty EventLoop线程隔离=人为制造所有资源不逃逸
- 阿里规范要求SimpleDateFormat用ThreadLocal=线程封闭
- 性能优化中"避免创建不必要的对象"本质是减少堆分配让逃逸分析生效
## 5. 认知变化
**以前我以为：** 线程安全是类的属性，加锁就好
**现在我认为：** 线程安全是使用方式的属性。核心是控制对象逃逸——不逃逸就天然安全。JVM逃逸分析证明这个原则不仅是编码规范，还是编译器优化的基础。
## 6. 最终压缩
> 线程安全的本质是控制对象逃逸。Thread Control Escape Rule：资源不逃逸出线程就安全。五种逃逸场景、五种修复策略。JVM逃逸分析是不逃逸的编译奖励——栈上分配、标量替换、锁消除。
