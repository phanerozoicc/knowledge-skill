## 1. 它解决了什么问题？
传统 ExecutorService.submit() 返回的 Future 可以逃逸到任何地方——存到集合里、跨方法传递、被遗忘。这导致三个问题：(1) 子任务生命周期不受控；(2) 一个子任务失败不会自动取消兄弟任务；(3) executor 生命周期和业务逻辑不绑定。
## 2. 它的核心矛盾是什么？
**灵活的 Future 逃逸 vs 安全可推理的并发边界。**
StructuredTaskScope 牺牲了"把 Future 传到任何地方"的灵活性，换来了"并发边界 = 代码块边界"的确定性。
## 3. 它的本质模型是什么？
StructuredTaskScope + try-with-resources 将 fork 出来的子任务生命周期绑定在代码块上——代码块结束 = 所有子任务保证已终止。失败自动传播（任一子任务失败 → 自动取消其他），取消自动级联（scope 关闭 → 所有子任务被中断）。
两种内置策略：
- **ShutdownOnFailure()**：任一子任务失败 → 取消其他所有子任务。适用于"所有子任务都必须成功"的场景。
- **ShutdownOnSuccess()**：任一子任务成功 → 取消其他所有子任务。适用于"多个数据源竞速，谁先返回用谁"的场景。
## 4. 它还能解释什么？
- **Kotlin 协程的 coroutineScope**：是同一模式——并发任务的生命周期应该被语法作用域约束。
- **Go 的 errgroup**：一组 goroutine 的 error 聚合和自动取消。
- **RAII**：并发任务也是一种"资源"，生命周期应该被作用域约束。
## 5. 认知变化
**以前我以为**：并发任务的生命周期管理就是用线程池 + Future，shutdown 靠规范约束。
**现在我认为**：结构化并发的核心洞察是——并发任务也是一种"资源"，应该像文件句柄、数据库连接一样被 try-with-resources 管理。代码块就是并发边界。
## 6. 最终压缩
> StructuredTaskScope 将 fork 的子任务生命周期绑定在 try-with-resources 代码块上——代码块结束保证所有子任务已终止，失败自动取消兄弟任务，消除线程泄露和手动取消逻辑。并发任务也是一种资源。
