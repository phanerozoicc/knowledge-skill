## 1. 它解决了什么问题？
传统模式中，线程池大小是并发度的硬限制——`newFixedThreadPool(10)` 意味着最多 10 个并发任务。虚拟线程便宜到几乎零成本，线程数不再有意义地限制并发度，但真正的瓶颈（数据库连接数、文件句柄、外部 API rate limit、内存）仍然有限。需要一种新的限流范式。
## 2. 它的核心矛盾是什么？
**线程便宜了，但资源没有变便宜。**
虚拟线程把"线程"从稀缺资源变成丰沛资源，但数据库连接、外部 API、文件句柄、内存缓冲区仍然是稀缺的。限流的维度从"限制 worker 数"下移到"限制资源访问并发数"。
## 3. 它的本质模型是什么？
**从"限 worker"到"限 token"。**
用 Semaphore（信号量）限制受保护资源的并发访问数，而不是限制线程数。线程池限制的是 worker 数量，信号量限制的是资源访问权（token）数量。
关键洞察：
- Semaphore.acquire() 阻塞时，虚拟线程 unmount，carrier 被释放
- Semaphore permit 仍被持有（保护了受保护资源的并发数）
- 阻塞结束后虚拟线程重新 mount，继续执行
- 线程数和资源限流数彻底解耦
## 4. 它还能解释什么？
- **Go 的 semaphore.Weighted**：限制 goroutine 对某个资源的并发访问，同样是"限资源不限制 goroutine"。
- **Bulkhead 模式**（Resilience4j）：为不同下游服务分配独立的线程池或信号量。
- **数据库连接池（HikariCP）**：`maximumPoolSize=20` 本身就是信号量——限制的是连接数而非线程数。
## 5. 认知变化
**以前我以为**：线程池大小 = 并发度上限，调优就是调线程池参数。
**现在我认为**：虚拟线程让线程数不再是有意义的限制维度。真正需要限制的是受保护资源（DB 连接、外部 API、文件）的并发访问数。限流方式从线程池迁移到 Semaphore。
## 6. 最终压缩
> 虚拟线程让线程从稀缺变丰沛，但真正的资源瓶颈（DB 连接、API rate limit）仍然有限。用 Semaphore 限制资源的并发访问数，而不是用线程池限制线程数。
