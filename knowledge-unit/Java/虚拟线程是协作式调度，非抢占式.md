## 1. 它解决了什么问题？
在传统 Java 中，每个线程都是 OS 线程的 1:1 包装（平台线程），OS 通过时钟中断实现抢占式调度——每过几毫秒，硬件时钟发一个中断，OS 强制切换线程。这保证了任何线程都不可能永久独占 CPU。
虚拟线程放弃了这套机制。因为虚拟线程的目标场景是高并发 I/O 密集型任务，这类任务天然有大量阻塞点，阻塞点就是天然的让出点。放弃抢占式调度换来了极低的线程切换开销。
## 2. 它的核心矛盾是什么？
**协作式的简洁 vs 开发者需要主动管理让出点。**
I/O 密集场景下这个矛盾不存在——阻塞点到处都是，调度自然发生。但一旦有人在虚拟线程里写了 CPU 密集计算（如图片处理、大 JSON 解析、加密运算），且没有在任何地方阻塞，这个虚拟线程就会一直占着 carrier，同 carrier 上的其他虚拟线程全部饿死。
## 3. 它的本质模型是什么？
虚拟线程使用协作式调度——仅在遇到 I/O、sleep、lock park 等阻塞点时 yield，纯 CPU 密集任务不会自动让出 carrier。
mount/unmount 的本质：虚拟线程执行时，JVM 临时把它的栈帧从堆内存拷贝到 carrier 线程的栈上；阻塞时再拷回堆。整个过程没有 OS 层面的上下文切换，只是 JVM 内部的内存操作。
## 4. 它还能解释什么？
- **Go goroutine 的演进**：Go 1.14 之前 goroutine 也是协作式的，只在函数调用点检查抢占标记。1.14 加上了基于信号的异步抢占。
- **Node.js 事件循环**：一个 callback 执行完才轮到队列里的下一个，长时间运行的同步代码会 block 整个 event loop。
- **Python asyncio**：`await` 就是显式的让出点。
## 5. 认知变化
**以前我以为**：线程调度都是操作系统的事，要么分时间片要么分优先级，开发者不需要关心。
**现在我认为**：虚拟线程把调度权交还给了开发者——默认情况下阻塞 I/O 就是让出点。但如果你在虚拟线程里写 CPU 密集计算，你需要主动插入让步点。
## 6. 最终压缩
> 虚拟线程是协作式调度：JVM 只在阻塞操作点 unmount 虚拟线程释放 carrier，纯 CPU 计算不会自动让出。这换来了极低的切换开销，但 CPU 密集型任务仍需平台线程 + 并行流。
