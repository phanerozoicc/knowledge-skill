# 学习者当前人形调度架构 + 一个命名素养点

## A. 当前工作架构(高价值情报)
L0-03 会话中,学习者披露了当前团队的调度架构现状:

> 「以 AGV 调度能力为基础,增加动作编排和流程编排,集中式调度;后期规划支持机器人自主规划路径,调度审核的请求式。」

### 拆解与教学含义
1. **以 AGV 调度为基础 + 动作/流程编排** —— 这正是 L0-03 预告的「②任务编排膨胀为技能编排」的实践印证。学习者团队已经在做这件事。
   → 含义:L2(任务分配)、L3-01(编排架构)对学习者是**直接可用**的,L4-02 可以深度对接他们的真实场景。
2. **集中式调度** —— 学习者团队当前选了 L0-02 里的「集中式架构」。这是合理的工程起点(简单可控),也印证了 L0-01 讲的"AGV 场景调度是上帝"。
   → 含义:L3-01 要讲清集中式 vs 分布式的边界,帮他们判断「何时该往混合式演进」。
3. **后期支持机器人自主规划 + 调度审核(请求式)** —— 这是向「混合式架构」演进的明确路线:车端有规划能力,但中央保留**审核/否决权**。
   → 含义:这是**架构演进**问题,正好对应后端的「单体→微服务→云边协同」演进。L3-01 和 L4-01 要重点讲这个演进路径,而且可以借用学习者熟悉的后端架构演进类比。也意味着 L2-04 的 CBS(集中式冲突消解)和「分布式/请求式审核」的对比会成为实战重点。

### 对课程的具体调整
- L3-01/L4-01 增设小节:「从集中式到混合式的演进路径」,直接对接学习者团队规划
- L2-04 不仅讲 CBS(集中式),还要对比「请求式审核」(混合式)的思路
- L4-02 人形调度,直接用学习者的真实场景(动作编排+流程编排)作案例

## B. 命名素养点(模块 vs 功能 vs 产物)
学习者连续两题把**模块名**答成了**产物/动作名**(冲突消解→实为"冲突消解器/模块";路径拓扑图→实为"拓扑管理模块,产物是拓扑图")。

### 这不算知识性错误
学习者能精准描述每个模块"做什么、产出什么",说明全景图已立住。缺的是一个**工程谈论素养**:架构讨论时要分清三层:
- **模块/组件**(名词,谁在做):冲突消解器、地图管理模块
- **功能/职责**(动词,做什么):冲突消解、路径规划
- **产物/数据**(名词,产出什么):无冲突路径、拓扑图、时间窗表

### 为什么这个素养重要
- 对应后端:「订单服务」(模块) vs 「订单状态流转」(功能) vs 「订单状态机」(产物)
- 学习者未来要设计自己的调度系统,这种分层谈论能力直接影响架构文档质量和团队沟通效率
- 已在学习记录里点出,后续课程中谈论模块时统一用「XX 模块/器」强调名词性,潜移默化强化

## 诚实状态
L0-03 全景图已扎实建立(4 个概念全部理解,只是命名层次需规范)。可推进 L0-04。学习者当前架构信息极有价值,将深度影响 L2~L4 的设计。
