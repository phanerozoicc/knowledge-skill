L0-01 · 为什么需要调度系统

阶段 L0 地基 难度:入门 前置:无 预计:40 分钟
🎯 这节课你将学会:用一句话和一个具体例子,讲清楚「没有调度系统会怎样、有了会怎样、调度系统到底在替业务解决什么问题」。这是后面所有内容的锚——如果你忘了为什么要学某算法,回到这一课。

先看一个没有调度的仓库

假设你是一个电商仓库的工程师,仓库里有 10 台 AGV(自动搬运车),用来把货架从存储区搬到拣货员面前——这是亚马逊 Kiva 系统的典型玩法。

现在来了 20 个订单,每个订单要搬一个货架。如果没有调度系统,每台车「自己看着办」,会发生什么?

⚠️ 没有调度的真实后果
  • 撞车:车 A 和车 B 都要去 3 号货架,在同一个路口顶在一起,谁也动不了。
  • 拥堵:主通道排成长龙,后面的车全堵死,吞吐量暴跌。
  • 忙闲不均:车 1 接了 5 个单累到没电,车 7 在角落闲到发霉。
  • 死锁:4 辆车在一个环形通道里互相让不出路,系统彻底卡死,要人工去推车。
  • 空跑:车送完货原路空车返回,白白跑一趟,能耗浪费 30%+。

这些不是吓唬人的极端情况——它们是 任何无协调的多车系统必然出现的现象,本质是「有限共享资源上的并发冲突」。你作为后端工程师,其实早就和这个问题的孪生兄弟打过交道了。

调度系统解决的问题,和后端系统里 「多个请求抢同一份共享资源」 是同一类问题:

  • 撞车 ≈ 并发写同一行数据(需要锁)
  • 拥堵 ≈ 数据库连接池打满 / 热点 key
  • 忙闲不均 ≈ 负载均衡没做好,某个实例被打爆
  • 死锁 ≈ 数据库/分布式锁死锁(经典的 A 等 B、B 等 A)
  • 空跑 ≈ 没有就近路由,请求跨可用区乱飞
一句话:AGV 调度系统 ≈ 一个「会动的、带物理实体的分布式任务编排 + 路由 + 锁服务」。 你后端打磨的直觉,大部分可以直接搬过来。

那调度系统到底是什么

剥掉所有花哨的概念,AGV 调度系统的核心定义可以这样写:

AGV 调度系统是在「有限资源」约束下,持续决定「每台车在什么时间、走什么路、干什么活」的软件系统,目标是让整个车队的某些 业务指标 尽可能好。

把这个定义拆开,里面藏着整个课程的地图:

定义里的词对应的课程模块
「有限资源」车数量、电量、充电桩、道路通行能力、路口 → L1 地图建模 / L2 冲突
「什么时间」时间窗、节奏、实时性 → L1 轨迹 / L3 实时性
「走什么路」单车路径 + 多车避撞 → L1 路径规划 / L2 MAPF
「干什么活」任务分配 → L2 任务分配
「业务指标尽可能好」优化目标(KPI)→ 下面专门讲

注意「持续决定」这三个字——调度不是一次性算完就完了,而是 一个不断运转的循环:车在动、任务在来、故障会发生、计划随时作废。这是它和「算一次的最优化问题」最大的区别。

业务怎么衡量调度好不好:KPI

「尽可能好」太虚,工业界用一组 关键指标(KPI) 来量化。这组指标是后面所有算法的优化目标——算法本身没有好坏,好坏是相对 KPI 说的。记住下面这五个,它们会反复出现:

KPI含义后端类比
吞吐量 Throughput单位时间完成的任务数(任务/小时)系统的 QPS / TPS
利用率 Utilization车辆真正在干活的时间占比CPU / 实例利用率
空驶率 Empty-run空车移动距离 / 总移动距离(越低越好)无效调用 / GC 开销
冲突率 Conflict rate发生冲突或被迫等待的次数锁等待 / 重试次数
时效 Latency任务从下达到完成的延迟(对订单很关键)请求 P99 延迟
🔑 关键洞察 这五个 KPI 经常互相打架。比如:为了降空驶率,让车就近接单 → 可能导致忙闲不均,利用率反而降;为了提吞吐,让车全速跑 → 冲突率上升。工业级调度的本质,就是 在这组矛盾的 KPI 之间找平衡点。没有银弹,只有权衡(trade-off)——这又和你做后端架构时的体感一模一样。

调度系统的三层视角

为了不让你在后面的课程里迷路,这里先给你一个「调度系统从上到下看是什么样」的预览。三个层次,记住这个结构:

层次回答的问题典型内容
L3 战略层
(任务管理)		「这批活,该不该现在干?谁牵头?」订单分组、优先级、批量、与上层 WMS/MES 的对接
L2 战术层
(调度引擎)		「具体哪台车干哪个活,走哪条路,不撞?」任务分配 + 路径规划 + 冲突消解(本课的主要内容)
L1 执行层
(车辆管理)		「这台车现在到哪了,下一步动作是什么?」状态机、位置上报、指令下发、故障处理

这个「战略-战术-执行」的三层切分,你一定觉得很眼熟:

  • 战略层 ≈ 业务的订单编排系统(决定这个订单走哪条业务流)
  • 战术层 ≈ 任务队列 + 调度器 + 负载均衡(哪个 worker 干哪个任务)
  • 执行层 ≈ 每个 worker 进程内的状态机(当前在执行哪一步、心跳、重试)
整个调度系统,就是这三层叠起来的一个实时分布式后端。你已经在 L3/L1 有大量经验,我们要补的主要是 L2 里那些「带物理空间」的算法。

一个具体例子:1 个订单的旅程

把上面的抽象落到一个具体场景。一个拣货订单进来,调度系统做了什么:

1. WMS(仓储管理系统)下发订单:「需要 3 号货架到 P12 拣货位」
        │
2.【战略层】订单进入调度,评估优先级,拆成 1 个搬运任务
        │
3.【战术层·任务分配】在 10 台车里挑一台:挑离 3 号货架最近、
        │                 且电量够、且当前空闲的车 —— 假设选中 AGV-04
        │
4.【战术层·路径规划】给 AGV-04 算一条路:当前位置 → 3 号货架 → P12
        │                 (A* 算法,避开已知障碍)
        │
5.【战术层·冲突消解】检查这条路会不会和别人撞 → 发现路口 K 要等 AGV-07
        │                 → 给 AGV-04 这段路加一个「时间窗预约」
        │
6.【执行层】把规划好的路线拆成「节点序列」下发给 AGV-04
        │                 (通过 VDA5050 协议,后面会讲)
        │
7. AGV-04 一边走一边上报位置 → 调度器持续监控
        │                 → 如果 AGV-07 卡住了,实时给 AGV-04 重算路
        │
8. AGV-04 到达 P12,任务完成 → 调度器释放资源,接下一个活

这 8 步就是一次完整的调度循环。本课程剩下的所有内容,都是在把这 8 步里的每一步拆开、讲深、做扎实。

📌 把这张图钉在脑子里 后面每学一个算法,都问自己一句:「它在上面这 8 步里的哪一步?它优化的是哪个 KPI?」能答出这两个问题,你就永远不会迷失在算法细节里。

小结

  • 没有调度的多车系统,必然出现撞车、拥堵、忙闲不均、死锁、空跑——本质是共享资源上的并发冲突。
  • 调度系统 = 在有限资源约束下,持续决定每台车「何时、走哪、干啥」,以优化一组互相打架的 KPI。
  • 核心 KPI:吞吐量、利用率、空驶率、冲突率、时效。没有银弹,只有权衡。
  • 三层结构:战略(任务管理)/ 战术(调度引擎)/ 执行(车辆管理),本质是一个实时分布式后端——你的主场。
