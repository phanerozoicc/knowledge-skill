L0-05 · 数学与算法前置(极简版)

阶段 L0 地基 难度:入门(但关键) 前置:无 预计:50 分钟
🎯 这节课你将学会:看懂接下来 L1、L2 全部算法所需的最小数学语言——什么是图、什么是搜索、什么是最优解、什么是复杂度。我们不展开任何数学证明,只建立够用的直觉。学完这课,你能看懂「在图上找最短路」这句话里的每一个词,并为 L1-03(Dijkstra)和 L1-04(A*)做好准备。
📌 这课为什么重要 你说过算法基础偏弱。这没关系——调度系统需要的数学其实很窄:主要是图论和一点点复杂度概念。不需要微积分、线性代数、概率论(那些只在高级优化/RL 里才用)。把这课吃透,你就拿到了进入 L1 的入场券。

一、图(Graph):调度系统的核心数据结构

整个 L1、L2 的算法,几乎都跑在「图」上。理解图,就理解了调度算法的舞台。

1.1 图是什么

图 = 节点(Node/Vertex)+ 边(Edge)。节点表示「地点」,边表示「地点之间的连接」。

B ────── C │ │ │ │ A ────── D ────── E

上面就是一个图:5 个节点(A~E),6 条边把它们连起来。在调度里:

  • 节点 = 仓库里的某个位置(路口、货架位、充电桩、停靠点)
  • 边 = 两个位置之间有一条可走的通道
图就是你天天打交道的东西:
  • 服务依赖图(服务 A 调用 B 和 C)
  • 数据库的 ER 图(实体和关系)
  • 社交网络的关注关系
  • Git 的提交历史(也是个图!)
唯一区别:调度的边上带着「距离/时间」,因为车走过去要花代价。

1.2 边权(Weight):代价

每条边可以带一个「权重」,表示走这条边的代价。代价可以是距离、时间、能耗——取决于你优化什么。

B ──3── C │ │ 2 4 │ │ A ──1── D ──5── E

现在每条边有了数字。A→B 距离 2,A→D 距离 1。「找最短路」就是:在所有从 A 到 E 的路径里,找边权之和最小的那条。

「最短路」不是几何上最短,是代价之和最小。代价可以是距离、时间、能耗——由你定义。这就是为什么同一个图,「最短时间路」和「最短能耗路」可能不一样。

1.3 有向 vs 无向

边可以分两种:

  • 无向边:A─B,双向可走(像普通通道)
  • 有向边:A→B,只能从 A 到 B(像单向通道,调度里很常见!)
无向: A ─── B 双向 有向: A ───▶ B 只能 A 到 B

调度里,为了防死锁,很多通道会被设计成单向(L2-05 会讲为什么单向化能防死锁)。所以你要习惯看有向图。

1.4 邻接表:图在代码里长什么样

图在内存里通常用「邻接表」存——每个节点记着「我能直接去哪些节点、代价多少」。

# 上面的图,用 Python 字典表示邻接表
graph = {
    'A': [('B', 2), ('D', 1)],
    'B': [('A', 2), ('C', 3)],
    'C': [('B', 3), ('D', 4)],
    'D': [('A', 1), ('C', 4), ('E', 5)],
    'E': [('D', 5)],
}
这就是一张路由表 / 服务依赖 map。后端里你肯定写过类似结构:`service_dependencies = {'订单服务': ['支付服务', '库存服务'], ...}`。一模一样。

1.5 栅格地图 vs 拓扑图(两种建图思路)

这是 L1-01 会深入讲的,这里先建直觉。物理空间有两种抽象成图的方式:

栅格地图(Grid)拓扑图(Topological)
长啥样把空间切成方格子,每格是个节点,相邻 8 格有边只在关键点(路口/货架)设节点,通道是边
节点数极多(1000㎡ 仓库可能上万格)少(几十到几百)
擅长精细避障、连续空间规划大规模、速度快、结构清晰
典型用SLAM、AMR 局部规划AGV 全局调度、Kiva 式

工业系统常两者结合:拓扑图做全局规划,栅格做局部精细避障。L1-01 会讲怎么选。

二、搜索(Search):算法的核心动作

2.1 什么是"搜索"

在图上「搜索」= 从起点出发,沿着边走,直到找到目标。所有路径规划算法(Dijkstra、A*)本质都是「搜索」,只是走法的聪明程度不同。

搜索 = 在一个分叉很多的空间里找东西。你站在 A,要去 E,但前面有无数岔路。算法就是在回答:「下一步该往哪走,才能又快又对地到 E」。

2.2 盲搜:BFS 与 DFS(L1-02 会讲)

最朴素的两种搜索:

  • BFS(广度优先):像水波扩散,一层层往外探。能保证在无权图上找到步数最少的路,但不一定是代价最小的。
  • DFS(深度优先):一条路走到黑,撞墙再回头。快但不保证最优。
BFS 探索顺序(从 A 出发,逐层扩散): 第1层: A 第2层: B, D ← A 的邻居 第3层: C, E ← B 和 D 的邻居 → 找到 E 时,路径 A→D→E 是步数最少的

这两个算法 L1-02 会动手实现。现在你只需知道:它们是「笨办法」,是 Dijkstra/A* 的基础铺垫。

2.3 带权搜索:为什么需要 Dijkstra 和 A*

BFS 只能找「步数最少」的路。但现实中边有权重(距离),你要的是「代价之和最小」的路。看这个例子:

A ──1── D ──5── E 路径1: A→D→E,代价 1+5=6 │ 2 │ B ──3── C ──4── (接D) 路径2: A→B→C→D→E,代价 2+3+4+5=14

BFS 会选路径1(2 步),但代价是 6。可能存在更优的吗? 这就要靠 Dijkstra(找全局最优)和 A*(又快又对)——L1-03、L1-04 的主角。

三、最优解 vs 可行解:工业系统的核心权衡

这是整个调度领域最重要的概念之一,你以后做工业系统会反复遇到。

最优解(Optimal)可行解(Feasible)
定义所有可能里最好的那个能用的、不违反约束的(不一定最好)
找它极难(尤其多车时,可能算不完)相对容易
成本计算时间可能爆炸快
何时要规模小、或代价敏感(每秒省几万块)规模大、实时性要求高(99% 工业场景)
工业调度的金句:「最好」是「好」的敌人。 花 10 秒算出最优解,vs 花 0.1 秒算出一个"还行"的解——后者在 100 台车实时跑的场景里完胜。这就是为什么工业界大量用启发式(heuristic):不一定最优,但够快够好。
这就是你后端天天遇到的权衡:
  • 缓存:不读最新数据(可行解),换速度
  • 最终一致性:不强一致(可行解),换可用性
  • 限流降级:不服务所有人(可行解),换系统存活
调度里的「放弃最优、要可行」是同一个思维模式。

四、复杂度(Big-O):算法贵不贵

复杂度回答一个问题:「输入变大时,算法会慢成什么样」。用 Big-O 记号表示。

4.1 直觉理解

记号名字n=10 时n=1000 时感受
O(1)常数11飞快,不随规模变化
O(log n)对数310极快(二分查找)
O(n)线性101000可接受(遍历一遍)
O(n²)平方1001,000,000规模一大就吃力
O(2ⁿ)指数1024💥 宇宙爆炸不可用,只对小规模可行
Big-O 不关心具体快慢,只关心增长曲线。O(n²) 在 n=10 时还行,n=1000 就崩了。调度系统的核心难点,就是很多问题的最优解是指数级的——这就是下一节要讲的 NP-hard。
你后端其实天天用复杂度直觉:
  • 为什么数据库要建索引?因为全表扫描是 O(n),索引查找是 O(log n)
  • 为什么 N+1 查询是性能杀手?因为它把 O(n) 变成了 O(n × 单次成本)
  • 为什么分布式锁要小心用?它是 O(参与方数) 的串行瓶颈
调度里完全一样:A* 是 O(n log n),CBS 在最坏情况是指数级——这就是为什么大规模调度不能蛮干。

4.2 实用记忆(够用)

你不用会推导复杂度,但要会感受这几个档位:

  • O(n) / O(n log n):工业可用,放心大规模
  • O(n²):中等规模可以(几百台车),上千就吃力
  • O(2ⁿ) / 指数级:小规模可以(几台车),稍大就必须用启发式

五、NP-hard:为什么调度"没有银弹"

这一节极重要,它解释了整个调度领域的根本困境。

5.1 一句话定义

NP-hard 问题:一类不存在已知快速(多项式时间)算法求最优解的问题。当规模变大时,找最优解的计算时间会指数级爆炸。

5.2 为什么调度大多是 NP-hard

坏消息:多车调度(MAPF)就是 NP-hard。意思是:

  • 2~3 台车:可以蛮力找最优
  • 10 台车:最优解要算几秒
  • 100 台车:最优解可能算几年都算不完
⚠️ 这意味着什么 对于工业级调度(几十上百台车),你永远不可能算出"最优"方案。你能做的,是在有限时间内算出一个「足够好的可行解」。这就是为什么 L2 充斥着各种启发式、近似算法、滚动重规划——它们都是在向 NP-hard 妥协。

5.3 应对 NP-hard 的工程哲学

整个 L2、L3 的设计,本质上就是在回答:「面对 NP-hard,工业上怎么活下来?」答案是一套组合拳:

  1. 近似算法:不追求最优,追求"够好且快"(如 CBS 本身就是次优的)
  2. 启发式:用经验/直觉裁剪搜索空间(如 A* 的启发函数)
  3. 分层/分治:把大问题拆成小问题(区域调度、分层规划)
  4. 滚动重规划:不一次算死,边走边算,适应变化
  5. 松弛约束:允许稍微次优,换可计算性
这就是你后端的日常啊:
  • 缓存 ≈ 近似算法(接受不是最新)
  • 布隆过滤器 ≈ 启发式(允许假阳性换速度)
  • 微服务拆分 ≈ 分治(每个服务管一小块)
  • 流式处理 ≈ 滚动重规划(不批量算死,边来边算)
  • 最终一致 ≈ 松弛约束(放弃强一致换可用性)
NP-hard 不是调度特有的噩梦,它是所有复杂系统的共同命运。 你已经在后端积累了大量"和 NP-hard 共存"的工程智慧,这些在调度里全部适用。

小结

  • 图 = 节点 + 边 + 边权;调度里节点是位置,边是通道,边权是代价。有向边用于单向通道。
  • 搜索 = 在图上找路;BFS/DFS 是笨办法,Dijkstra/A* 是聪明办法(L1 会学)。
  • 最优解 vs 可行解:工业调度 99% 选可行解——「最好」是「好」的敌人。
  • 复杂度:O(n²) 是分水岭,指数级只对小规模可行。
  • NP-hard:多车调度是 NP-hard,没有银弹,只能靠近似/启发式/分层/滚动重规划/松弛。但这套应对哲学你后端早就会了。
