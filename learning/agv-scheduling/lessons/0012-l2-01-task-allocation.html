L2-01 · 任务分配:谁来干这个活

阶段 L2 多机调度核心 难度:中等 前置:L1 全部 预计:50 分钟
🎯 这节课你将学会:从单机进入多机的第一道关——任务分配:一批任务来了,该怎么决定每台车干哪个?你会理解三种主流策略(贪心 / 匈牙利算法 / 拍卖),知道它们在"全局最优 vs 实时性"上的取舍。这是 L2 的入口,相对友好,为后面 L2-04(CBS)做铺垫。
📌 你在哪一层 L2 是整个课程最难也最核心的阶段。但这第一课(L2-01)是你的舒适区——任务分配本质就是后端的负载均衡,你已经会了。我们快速建立正式语言,重点放在三种策略的取舍上。

问题:把任务分给车

L1 你解决的是"一台车怎么从 A 到 B"。现在多台车、多个任务,第一个问题就是:哪个任务交给哪台车?

形式化一点:有 N 个任务、M 台车,每个"任务-车"组合有一个代价(通常是车到任务起点的距离)。要找一个分配方案,让总代价最小(或某种全局指标最优)。

💡 代价怎么算?别每次都跑 A* 严格说,代价是"车到任务起点的路径长度"。但任务分配阶段不需要跑完整 A*(太慢,几百台车 × 几十个任务就是几千次规划)。工业上通常用直线距离(欧几里得)快速估算就够了——因为分配只在乎"远近"的相对关系,不在乎精确路径。真正的 A* 规划在分配完之后才跑(只给中标的车跑)。这是"用粗糙估算做决策,用精确计算做执行"的常见工程套路。
这就是负载均衡器选实例。一堆请求(任务)进来,负载均衡器决定每个请求打给哪个后端实例(车)。代价 = "把请求路由到该实例的延迟/负载"。你已经天天在做这件事。区别:后端的代价通常是"队列长度/CPU",调度里的代价是"物理距离"——通常用直线距离快速估算,精确 A* 留到分配完才跑。

三种主流策略(按"从笨到聪明"排)

策略 1:贪心(Greedy)— 就近分配

最简单:每个任务来,找离它最近的空闲车,分给它。或者反过来:每台空闲车,抢离自己最近的待办任务。

def greedy_allocate(tasks, vehicles):
    allocation = {}
    for task in tasks:
        # 找最近的空闲车
        v = min(vehicles, key=lambda v: distance(v, task))
        allocation[v] = task
        vehicles.remove(v)    # 这车忙了
    return allocation

优点:极快,实现简单,实时性好。每个任务来了立刻分配,不等。

缺点:短视,不保证全局最优。经典反例:

⚠️ 贪心的陷阱 任务 T1 离车 V1 很近(代价 1),离 V2 远(代价 10)。贪心会把 T1 给 V1。
但任务 T2 离 V1 中等(代价 2),离 V2 极远(代价 100)。
贪心接着把 T2 给 V2 → 总代价 1+100=101。
而最优解是:T1 给 V2,T2 给 V1 → 总代价 10+2=12。
贪心因为短视,错过了总代价低 8 倍的方案。

策略 2:匈牙利算法(Hungarian)— 全局最优

贪心短视,因为它一个一个分配。匈牙利算法一次性考虑所有任务-车组合,求全局最优分配。

它把问题建模成:造一个 M×N 的代价矩阵(每行一辆车,每列一个任务,格子里是该车干该任务的代价),然后找一种"每车一任务、每任务一车"的分配,让选中格子之和最小。

优点:全局最优。在这个小例子里,它能找到代价 12 的方案(贪心只能找到 101)。

缺点:慢。复杂度 O(n³),任务和车一多就吃力。而且它要求"一次性看全部任务"——但实时系统里任务是一个个流式来的,你等不齐"全部任务"再分配。

匈牙利算法 ≈ 后端的批处理调度:攒一批请求一起优化分配,质量高但要等。贪心 ≈ 逐请求路由:来一个转一个,快但可能次优。这个取舍你后端天天在做。

策略 3:拍卖机制(Auction / CN)— 分布式协商

前两种都是中央独裁。拍卖机制相反:中央喊任务,各车自己出价(基于自己的代价评估),价优者得。

def auction(task, vehicles):
    bids = {}
    for v in vehicles:
        bids[v] = v.compute_bid(task)   # 每台车自己评估"我干这个要花多少代价"
    winner = min(bids, key=bids.get)     # 出价最低(代价最小)的赢
    return winner

优点:分布式、可扩展。车数很多时,中央不用算所有组合,只要收出价。容易加新车(它自己学着出价就行)。也契合你规划的"车端有自主能力 + 中央审核"的混合架构。

缺点:需要通信往返(喊任务→收出价→宣布中标),有延迟;出价策略设计不好会次优。

拍卖 ≈ 服务发现 + 客户端负载均衡(如 Ribbon):不再由中央独裁,而是各实例广播自己的负载/能力,请求方按规则挑。你规划的"车端规划+调度审核"架构,本质就是一种带审核的拍卖——车端出价(自己规划的方案),调度审核(冲突/死锁检查)。

三者对比:经典的工程权衡

贪心匈牙利拍卖(CN)
最优性❌ 次优(短视)✅ 全局最优≈ 近似最优(取决于出价)
速度✅ 极快❌ O(n³)中等(要通信)
架构中央中央分布式
可扩展好差最好
实时性✅ 流式❌ 要等齐一批✅ 流式
后端映射逐请求路由批处理调度服务发现+客户端LB
📌 工业实践:不选一个,而是组合 真实系统常常分层:
  • 高频流式任务用贪心/拍卖,保证实时
  • 低频批量优化(比如每小时的全局重均衡)用匈牙利,纠正贪心积累的偏差
这就像后端:日常用缓存+快速路由,定期跑批校正数据。没有银弹,只有权衡——L0-05 的 NP-hard 教训在这里又一次应验。

任务分配和路径规划的关系(伏笔)

注意一个关键点:"代价"是路径相关的(车到任务起点的距离,通常用直线距离估算)。所以任务分配和路径规划有依赖——你得先知道每台车到每个任务大致多远,才能分配。

但这只是单机代价。真正的难点在后面:分完任务、各车开始规划路径后,它们会互相冲突。任务分配阶段完全没考虑冲突——它只看了"谁离得近",没看"会不会撞"。这就是 L2-02(冲突分类)和 L2-04(CBS)要补的洞。

🔑 这就是为什么 L2 要拆成三步
  1. 任务分配(本课):谁干啥——基于单机代价
  2. 路径规划:各自 A*——单机最优路径
  3. 冲突消解(L2-04 CBS):发现彼此冲突,重算——多机协调
每一步都以为前一步搞定了,结果下一步发现问题。这是多机调度的本质复杂性。L2-06 会把三步串成完整流程。

人形伏笔

对人形,任务分配多一个维度:能力匹配。
  • AGV 都是同构的(谁都能搬货架),分配只看距离
  • 人形是异构的——不是每台都会"泡咖啡"或"开门"。分配时要看"谁会这个技能"
这对应后端的能力路由:不是所有实例都能处理所有请求(有的有 GPU、有的有特殊许可证),负载均衡要考虑实例能力。人形任务分配 = 带能力约束的负载均衡。L4-02 会展开。

小结

  • 任务分配 = 负载均衡选实例的调度版,代价是物理距离(通常直线估算,A* 留到分配后)。
  • 三种策略:贪心(快但次优)、匈牙利(最优但慢)、拍卖(分布式可扩展)。
  • 工业实践常组合:流式用贪心/拍卖,批量用匈牙利纠偏。
  • 关键:任务分配只看单机代价,不看冲突——冲突是 L2-02/L2-04 的事。
  • 人形多了"能力匹配"维度(异构)。
