LAB-01 · 代码导读:五次散步读下一个调度核心

实训课(插入于 L2-02 与 L2-03 之间) 难度:中 前置:L2-02 预计:5 次散步 × 35~45 分钟
🎯 这节课你将学会:不是新知识,而是把 L2-02 的理论钉进那 1917 行工业代码里。读完你能独立讲出两件事:一次 tick 的完整流水线,和一条预留从出生到死亡经过谁的手。这两件事讲得出来,这套架构你就真的拥有了——后面 L2-04 的 CBS 就是在这套代码上换规划器,地基必须先踩实。
关于"读起来吃力"

这不是能力问题,是方法问题:1917 行工业代码本来就不该从第一个文件顺读到最后一个。你在后端世界里也不会 linear 读一个陌生服务——你会先跑起来、先看数据模型、先看测试。这节课就把那套直觉搬到调度代码上:一张地图、一条主线、五个检查点,分五次走完。每次散步只有 300~400 行核心代码,在 working memory 预算之内。

先立心法:工业代码怎么读

  1. 先跑再读。没见过运行的代码,读的是死的。第一件事永远是让 demo 和测试在你手里跑绿。
  2. 先名词,后动词。models.py 里全是名词(Reservation、Vehicle、EdgeId),其他模块全是围绕这些名词的动词。名词不熟,动词全是天书。
  3. 自底向上按依赖读,不自顶向下按执行读。被依赖最多的(models)先读、读得最透;总指挥(scheduler_loop)最后读,那时它每一步调用的东西你都认识了。
  4. 测试当用法文档。36 个测试就是 36 个"这个类该怎么用、边界在哪"的例子,比任何文档都诚实。
  5. 带一条主线问题读。本课主线:一条预留,从出生到死亡,经过谁的手?每读一个模块,问自己"它对这条生命周期负责哪一段"。
  6. 时间盒 + 检查点。每次只走一站,做完检查点再走。贪多必噎。

另外,代码里已经埋好了配套路标:💡 是学习点(对应课程哪一课)、🔑 是关键正确性、⚠️ 是踩过的坑。这次阅读它们就是你的导游。

第三步:interval_index.py(10 分钟)+ metrics.py 顺路(5 分钟)

只看一个方法:overlaps()(interval_index.py:58)。它是冲突检测的全部逻辑,分三支:节点桶 → VERTEX;同向边桶 → FOLLOWING/EDGE;反向桶(interval_index.py:109 的 rev_key)→ SWAPPING。为什么包一层而不直接用 intervaltree?——防腐层:第三方库的 API 不泄漏到上层,将来换实现只改这一个文件。metrics.py 是 55 行计数器,扫一眼即可。

检查点 1.1:EdgeId("A","B") 和 EdgeId("B","A") 是同一个资源吗?这个设计为什么关键?

不是,是两个不同资源。正因为分开,同一时间段两条都被占用时,查反向桶才能发现"两车在同一条物理路段上迎面而行"(SWAPPING)。如果边是无向的、A→B 和 B→A 共用一个键,就分不清"相向"和"同向",对向冲突会漏检——工业上干脆用单行道根治它,也是同一个认识。

检查点 1.2:Reservation 为什么必须是 frozen(不可变)?

因为它要被 live 表和快照共享。快照拷贝区间树时,payload(Reservation 对象)是直接共享的(interval_index.copy 的注释写了这点)。如果对象可变,主循环原地改一个字段,规划线程手里的"冻结"快照就被偷偷改了——COW 的前提是 payload 本身不可变。所以改字段必须 replace() 生成新实例(reserve_batch 里就是这么填租约的)。

散步 2 · reservation_table.py:心脏(全课最重要的一站)

⏱ 40 分钟 scheduler/reservation_table.py(276 行)

先读模块 docstring(reservation_table.py:1)——它列出了全部公开操作,正好是"预留的一生"的中后段。然后按这个顺序精读五个操作:

  1. reserve_batch(reservation_table.py:88)——事务性提交。难点在两阶段检查(reservation_table.py:126):① 对已提交索引查;② 对批内已接受成员查(防自冲突)。建议读两遍,第二遍问自己:如果少了第②步,什么会坏?(同一轨迹的两个预留各自通过检查、互相矛盾地进表。)
  2. confirm_passed(reservation_table.py:188)——ack 机制。docstring 里那句"这是区分正常完成和异常停滞的唯一可靠信号"是血泪:开发时踩过的坑就源于此。
  3. expire_stale(reservation_table.py:207)——⚠️ 注释(reservation_table.py:212)必读:只按 lease_deadline 判,绝不按 t_end 判。下面动手 2 就是让你亲手把这个坑重新踩一遍。
  4. release_agent(reservation_table.py:233)——掉线清场,最短。
  5. rollback(reservation_table.py:241)——按 rid 精确撤销一个已提交批次,供滚动重规划用。

可跳过:_bump_conflict_metrics(纯计数)。值得注意:提交阶段(reservation_table.py:172)的注释解释了为什么不需要"失败反向删除"的补偿路径——因为检查全过才动手写,且 index.add 对合法区间不会失败。事务的回滚是靠不写实现的,不是靠写了再删。

检查点 2.1:为什么绝不按 t_end 判失效?误清的连锁反应是什么?

t_end 只是"预期离开时间"。车可能正常驶过、只是上报(ack)还在路上(comms 滞后)。若按 t_end 判:正常车的预留被误清 → 车进 reaped 名单 → 被标 dirty → 每 tick 重规划 → 每 tick 又被清……车永远停在起点。租约(= t_end + 5s 余量)才是"真的出问题了"的可靠信号。

检查点 2.2:t_end 已过但未确认的残留预留,为什么不会误挡未来规划?

未来候选的时间窗 t_start ≥ now ≥ 残留的 t_end,半开区间 [a,b) 在 b ≤ c 时不可能与 [c,d) 重叠(overlaps_time 的实现就是这句话)。所以留着等 confirm 是安全的;车真挂了,租约兜底。这是"宁可慢半拍,不可错杀"的容错取向。

散步 3 · snapshot.py + planner.py:快照与规划器

⏱ 45 分钟 scheduler/snapshot.py(56 行)→ scheduler/planner.py(286 行)

snapshot.py 只有 56 行:一个 Graph(邻接表,你 L1-01 建的图就是它)+ 一个 Snapshot(时钟、图、车队、预留索引的私有副本、horizon)。它的全部意义在 docstring:规划线程只读快照,绝不碰 live 表。

planner.py 只需要读两个灵魂方法 + 一个诚实声明:

  1. plan() 主循环(planner.py:77)——状态是 (节点, 时间),这就是 L1-04 的 A* 升级成时间扩展 A*。两种族动作:过边(候选预留构造在 planner.py:125——每一步都现场造 EDGE+NODE 两条预留去查表)和 wait(planner.py:152——原地等一拍,低优先级让路的机制)。
  2. _conflicts_others(planner.py:176)——只和别人冲突,忽略自己。为什么?docstring 给了答案,和主循环"先 rollback 再重规划"是配套的。
  3. h 恒 0(planner.py:190 ~ planner.py:200)——诚实声明:现在退化成 Dijkstra。正确性不受影响,只是慢。工业版怎么做,docstring 里写了方案(反向 BFS 预计算跳数),也是本课综合挑战。

必读:文件底部 prioritize_and_plan(planner.py:265)的 ⚠️ docstring——它解释了为什么主循环不用它(固定快照不跨智能体一致),这是理解散步 4 的钥匙。可跳过:_reconstruct、_cheapest_edge(机械辅助)。

检查点 3.1:规划时为什么要忽略自己的预留?

重规划时,新轨迹本来就要覆盖旧轨迹的时空——主循环会先 rollback 旧计划再规划新的。如果不忽略自己,新车速轨迹会和"自己还没被撤销的旧预留"冲突,规划永远失败。后端类比:事务和自己未提交的数据不算冲突。

检查点 3.2:prioritize_and_plan 的输出为什么不能直接 commit?

所有智能体共用同一张固定快照,彼此看不到对方的候选计划——两个车可能都规划进同一个空闲时空格,同时提交就是重复占位。要么每接纳一个计划就落表、给下一辆重拍快照(主循环的做法),要么中心式消解冲突(CBS,L2-04)。这个函数只是教学/诊断用。

散步 4 · scheduler_loop.py:总指挥

⏱ 35 分钟 scheduler/scheduler_loop.py(236 行)

读这一个文件就读一个方法:tick()(scheduler_loop.py:108)。它是唯一写者,一条 tick 流水线(行号为锚):

  1. 时钟推进 dt(scheduler_loop.py:114)——调度拥有时钟,不读墙钟,所以测试是确定性的;
  2. 摄入上报 + 确认(scheduler_loop.py:117)——注意确认转手就调了散步 2 的 confirm_passed;
  3. 离线检测(scheduler_loop.py:131)——哨兵判定 last_heartbeat >= 0 在 scheduler_loop.py:135,超时则 release_agent;
  4. 清租约(scheduler_loop.py:142)——被清的车进 reaped 名单;
  5. 标 dirty(scheduler_loop.py:151)——只有两类车重算:被清理过的、有目标却没计划的;按优先级排序(scheduler_loop.py:163);
  6. 逐车重规划:先 rollback 旧计划(scheduler_loop.py:176)→ 重拍快照(scheduler_loop.py:182)→ 规划 → commit(scheduler_loop.py:192);规划失败标 WAITING 下 tick 再试(scheduler_loop.py:190);
  7. 到达清目标(scheduler_loop.py:206)。
这个模型你其实天天在用:单写者 = 单线程 event loop(Node/Redis 的并发哲学:一个线程改状态,重活丢给别处);每车规划前重拍快照 = 读已提交(read committed)——每个事务开始时读最新的已提交状态,绝不读半截数据。规划器则是无状态计算服务:不持有任何状态,进快照、出结果,天然可以水平扩到线程池(README 诚实声明了:架构支持,demo 未实际并发)。
检查点 4.1:为什么每辆车规划前要重新拍快照,而不是全队共用一张?

因为第 1 辆(最高优先级)刚把它的轨迹 commit 进了 live 表。第 2 辆必须看到这份新提交才能正确避让;如果还用 tick 开头拍的旧快照,两辆车会"各自以为某时空空闲"而撞车——这正是 planner.py 底部 prioritize_and_plan 警告的那个问题,主循环用"每车 re-snapshot"这一步根治了它。代价是每车一次区间树拷贝,换来正确性,值。

散步 5 · sim/ 与 tests/:世界替身与行为规格

⏱ 40 分钟 sim/world.py(94 行)→ sim/scenarios.py(90 行)→ tests/(5 文件 36 测试)

sim/world.py 只有一件聪明事:VehicleMover(sim/world.py:48)是物理世界的替身——它把已提交的预留反向翻译成 PositionReport(心跳+位置)和 Confirmation(ack),喂回 tick 的入参。真车里这两样东西来自车载控制器经通信层上报,VDA5050(L3-03)讲的就是那条链路。

这里藏着散步 2 的深层答案:reports_for 只对 NODE 预留发确认(sim/world.py:83)。EDGE 预留永远没人逐条 ack——已走完的边留在表里无害(检查点 2.2 讲过为什么),它的退场要么等车辆到达/重规划时的整批 rollback,要么靠租约到期。你重读 expire_stale 时应该有"原来如此"感:租约不是防呆冗余——对边预留来说,它是唯一逐条、及时的清理机制。

sim/scenarios.py:场景 1(sim/scenarios.py:31)三车汇合避让;场景 2(sim/scenarios.py:58)V2 掉线→释放→重分配。

tests/ 按这个顺序读,每个测试函数名就是一条规格:

  1. test_reservation.py —— 表的基本契约 + 事务原子性(中途冲突整批回滚);
  2. test_lifecycle.py —— confirm → lease 过期 → release 的完整链路;
  3. test_snapshot.py —— 钉死"规划期间主循环改表,快照纹丝不动"的隔离性;
  4. test_planner.py —— 时间扩展 A* 的正确性 + wait 避让;
  5. test_anomaly.py —— 掉线/超时/死车 → 重规划,最有戏的一份。
检查点 5.1:VehicleMover 发的 Confirmation,本质上替真实系统里的什么?

车端上报的"我已离开资源 R"——真实系统里这是车载控制器过完一个节点/路段后,经通信层发给调度的心跳附带信息(或独立消息)。它和 PositionReport 一起,构成调度感知世界的全部输入。没有它,调度无法区分"正常走完"和"卡死不动"(散步 2 的核心教训)。

常见追问(读代码时几乎一定会问的两个问题)

追问一:时间窗口是怎么划分的?移动要多少个窗口,是路径长度 ÷ 速度吗?

一半对,一半不对。"距离 ÷ 速度"确实存在,但它发生在建图的时候,不在调度运行时:

  1. 边权就是时间。Graph.adj(snapshot.py:27)里每条边带的不是米,而是"过这条边要几秒"(MAP_ADJ 里的 5.0、3.0…)。建图时人已经替你做了 距离÷速度=时间(L2-02 的公式)。所以规划器从不知道"速度"这个概念,它看到的世界已经是时间;要改车速或表达拥堵,改边权就行(这就是 L1-01 埋的"动态权重"伏笔)。
  2. 没有预先划分的全局时间格子。这套代码的时间窗不是把时间轴切成一格格再数格子,而是每次移动时现场生成的连续半开区间 [t_start, t_end)。规划时只有一句累加:到达时刻 = 出发时刻 + 边权(planner.py:116)。
  3. 一次移动产生几个窗?过一条边 = 2 条:EDGE [出发, 到达) + 到达节点的 NODE dwell [到达, 到达+1s)。整条路径 = 跳数 条 EDGE + (跳数+1) 个 NODE dwell——动手 1 的 9 条就是这么来的。
动作生成的窗口窗口长度
过边 A→B1 条 EDGE [t, t+通行时间)边权(建图时定)
到达节点 B1 条 NODE [t′, t′+node_dwell)node_dwell,默认 1s(路口减速占用)
原地等待1 条 NODE [t, t+time_step)time_step,默认 1s

唯一的"离散粒度"是 wait:只能整拍整拍地等(time_step),因为搜索状态 (节点, 时刻) 必须可枚举。也有的工业实现反过来把整个时间轴量化成固定槽位(slotted time),实现更简单但会浪费槽内碎片——本代码选了连续时间窗,更接近真实。

追问二:车延迟了、甚至坏在半路,预留表怎么处理?

分两种情况,防线不同:

情况 A:只是慢(延迟几秒,还在动)。小延迟被租约余量吸收:预留的 lease_deadline = t_end + 5s(reservation_table.py:38),迟到几秒的 confirm 照样有效;而过了 t_end 的残留窗口不会挡别人(检查点 2.2 的半开区间性质)。延迟在余量内,预留表层面就无感——窗口不误清、也不误挡。物理上的跟车安全不靠这张表,靠安全余量和车载安全层,那是另一层防线。

情况 B:彻底不动了(坏在半路)。又分通信是否还活着,构成三层防线:

防线触发条件系统动作代码
① 失联清场心跳超时(默认 6s 无上报)标 OFFLINE → release_agent 清掉它全部预留 → 空间让给别人scheduler_loop.py:131;测试 test_stale_heartbeat_marks_offline_and_releases
② 卡住重规划通信活着但 confirm 停了 → 租约(预留结束 + 5s)到期expire_stale 清残留 → 车进过期名单 → 标 dirty → 从它当前(卡住的)位置重规划;还坏着就每隔一个租约周期再来一轮reservation_table.py:207
③ 暂堵等待规划失败(暂时被别人堵死)标 WAITING,下一 tick 再试,不死循环烧 CPUscheduler_loop.py:190

demo 的场景 2 演示的是防线 ① 的处理动作(手动把 V2 置 OFFLINE + 释放,看 V3 重规划);心跳超时的自动判定本身在 tick 第 3 步,由 test_anomaly.py 钉死。

⚠️ 两个诚实边界(读代码时值得停下来想的)
  1. 渐进延迟检测没接线。slip_threshold 字段在 Vehicle 和 SchedulerConfig 里都声明了("落后计划多少秒触发重规划",scheduler_loop.py:72),但 tick() 的 dirty 判定目前只看"被清理过 / 有目标无计划"两个条件——落后但没超租约的车不会触发重规划,要等到租约到期才被兜住。把它接上是一个绝佳的课后练习(提示:比较"位置最后一次变化的时间"和"计划中本该到达的时间"),也是 L3-02 滚动重规划的正式内容。
  2. "尸体占路"是物理问题,时间窗管不了。release 之后,时空表"看起来"空了,但坏车 physically 还横在路上——调度模型只认时间窗,不认永久障碍,别的车可能规划出一条"从尸体上开过去"的路。工业做法:把该节点/边标记封锁(挂一条超长预留,或临时把边权改成 ∞),恢复后再解除,或派人拖车。这正是 L3-04"地图临时封锁"要讲的内容。

小结

  • 工业代码自底向上按依赖读:名词(models)→ 索引 → 心脏(reservation_table)→ 快照与规划器 → 总指挥(loop)→ 替身与规格(sim/tests)。
  • 主线一条:预留的一生 = _build_reservations 出生 → reserve_batch 入职 → live 表(被快照读)→ 四种退场(confirm / expire / rollback / release)。
  • 四个正确性支柱:单写者、事务原子、租约判失效、每车重拍快照。每个支柱都有一个亲手实验钉住它。
  • 架构 = 你熟悉的后端模式的重新组合:event loop + read committed + 无状态计算服务 + 测试替身。
