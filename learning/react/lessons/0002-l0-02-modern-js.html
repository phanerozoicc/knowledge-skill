二、深水区①:解构 + 展开 = 不可变更新(React 的命脉)

先看代码。这是 React 里更新状态的标准姿势,今天只看 JS 语法,下周它就是你的日常:

// 数组:追加一项,不改原数组
setItems([...items, newItem]);

// 对象:改一个字段,不改原对象
setUser({ ...user, name: 'AGV-04' });

// 嵌套:改「数组里 id=2 的那一项」——展开嵌着展开
setTasks(tasks.map(t => t.id === 2 ? { ...t, done: !t.done } : t));

为什么必须造新的、不能改旧的(tasks.push(x) 多顺手)?

React 判断「状态变没变」靠引用比较(Object.is)——引用就是版本号。你 push 了,内容变了但引用没换,React 视而不见,界面纹丝不动。这不是风格偏好,是 React 的检测机制决定的硬约束。

你改了缓存里的内容、但没换 key,下游全都在「命中」旧值——系统看起来「坏了」,其实是谁都没收到变更通知。React 的 state 就是这个逻辑:引用换了才算「失效通知」。L1-02 讲重渲染时会把这套机制完整展开;今天先钉住结论:改状态 = 换引用。

三、深水区②:map/filter——React 列表渲染的地基

React 把列表渲染到界面上,唯一的惯用法就是你闭着眼能写的 Stream:

const items = [
  { id: 1, text: '排查 3 号充电桩离线', done: false },
  { id: 2, text: '导出昨日任务报表', done: true },
];

// 过滤 + 映射,和 Kotlin / Java Stream 同构:
const pending = items.filter(t => !t.done);        // 未完成
const labels  = pending.map(t => t.text);          // 文本数组

// React 里唯一的增量:map 出来的不是字符串,是「界面元素的描述」:
// items.map(t => <li key={t.id}>{t.text}</li>)   // L1-01 见

注意和 Java Stream 的一个小区别:JS 的 map/filter 是立即执行的(没有惰性求值和终端操作那套),每一步都实实在在产出新数组。数组不大时无所谓;性能敏感时的优化思路 L3 讲。

四、深水区③:闭包——hooks 的头号前置

闭包的定义一句话:函数记住它出生时作用域里的变量(的绑定),离开出生地也带着。

function makeCounter() {
  let count = 0;                    // 被「记住」的变量
  return () => ++count;             // 这个函数出生时,把 count 绑定揣进了兜里
}
const next = makeCounter();
next(); // 1
next(); // 2  ← makeCounter 早就返回了,count 还活着
Java/Kotlin 的 lambda 也能捕获变量,但只能捕获 effectively final 的;JS 闭包更强——捕获的是变量本身(绑定),不是值的快照,变量后来变了,闭包里读到的也变。

这个「更强」正是 React 头号 bug 的来源:每次渲染,组件函数重新执行,产生一批新闭包。旧闭包里读到的旧状态(stale closure)——「我明明 set 了,为什么读出来还是旧值」——是 hooks 时代最经典的困惑。今天不展开,记住「每次渲染 = 新的一批闭包」这句话,L1-04 会回来收这笔账。

五、异步:你其实已经会了(2 分钟)

async function refreshTasks() {
  const res  = await fetch('/api/tasks');        // ≈ CompletableFuture
  const data = await res.json();
  return data;                                    // 调用方可以继续 await
}

Promise ≈ CompletableFuture,async/await ≈ 协程的 suspend——「看起来同步,实际让出」。JS 的运行时是单线程 + 事件循环,和你熟悉的 Netty 反应器模型同构:await 不占线程,只是挂到「完成后继续」的队列里。所以前端没有锁竞争问题,但有「一个长任务卡住整帧渲染」的问题——这就是 L0-01 说的 16.7ms SLA 的另一面。
